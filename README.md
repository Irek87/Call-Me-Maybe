# Call-Me-Maybe

## Description
**Call-Me-Maybe** is a small function-calling router powered by a local LLM (via `llm_sdk`).  
Given:
- a list of **function definitions** (name, description, parameter schema), and
- a list of **user prompts**,

the program produces a JSON output where each prompt is mapped to:
- a selected function **name**, and
- extracted **parameters** (as JSON).

**Goal:** implement a function-calling pipeline using **constrained decoding** ideas (token-by-token guidance) to reliably select a valid function name and generate valid JSON parameters.

## Algorithm explanation (Constrained Decoding)

### 1) Function name selection (token-level constraint)
The program selects the function name using a token-by-token decoding loop:
1. Build a prompt containing available function names/descriptions.
2. For each decoding step `i`, restrict the next token to a precomputed set `valid_funcs_tok_ids[i]`,
   where `valid_funcs_tok_ids[i]` contains token IDs that appear at position `i` in any valid function name.
3. Choose the token with the highest logit among the allowed set and append it.
4. Stop once the decoded string matches one of the known function names.

This ensures that each generated token is *compatible with at least one function name token at that position*.

**Note:** This implementation is a simplified constraint approach (position-wise union).
A stronger variant would track *candidate sequences* (state machine) to guarantee that the entire generated
token sequence matches exactly one known function name.

### 2) Parameter extraction (JSON generation + parse loop)
Parameters are generated by:
1. Prompting the model with the selected function definition and the user prompt.
2. Starting the output with a JSON prefix: `{"parameters": { "<first_param>":`
3. Greedy-generate tokens until the partial output becomes valid JSON.
4. Attempt `json.loads()` after each token; stop as soon as parsing succeeds.
5. Enforce a maximum token limit to prevent infinite generation.

This approach aims to produce syntactically valid JSON, and relies on the function schema in the prompt
to guide type correctness.

---

## Design decisions
- **Simple pipeline first:** separate function selection and parameter extraction as two steps, which reduces complexity compared to generating a full nested JSON structure in one pass.
- **Precomputed token constraints for function names:** function names are tokenized once and used to build per-position allowed token sets.
- **Fail-safe function (`fn_NULL`):** appended to the function list to provide a fallback when no function matches a prompt.
- **JSON parsing as a stopping criterion for parameters:** stops generation at the first point where the output is valid JSON.

## Performance analysis

### Accuracy
- **Function name selection:** generally accurate on the provided test prompts when the model follows instructions.
  However, the current position-wise token constraint does not guarantee the final token sequence is a valid name
  unless the string matches an existing function name (which is checked).
- **Parameters:** the JSON-parse stop criterion ensures valid JSON syntax, but semantic correctness depends on the model.
  Complex strings (e.g., regex, escaping) are more error-prone.

### Speed
- The implementation performs *one forward pass per generated token*.
- Function selection is relatively fast because function names are short.
- Parameter extraction can be slower because it may require many tokens before reaching valid JSON.

Key factors affecting speed:
- Prompt length (longer prompt = slower inference per step)
- Number of generated tokens (especially in parameter decoding)
- Greedy decoding without KV-cache exposure (SDK limitation)

### Reliability
- Function selection is bounded by the maximum function-name token length.
- Parameter generation is bounded by `max_tokens` (currently 777).
- JSON parsing provides a concrete correctness check for syntax, but does not guarantee schema correctness.

---

## Challenges faced
- **Stopping conditions:** reliably deciding *when to stop* generation is difficult. For parameters, stopping on valid JSON parsing is simpler than relying on special tokens.
- **JSON escaping and regex strings:** generating properly escaped JSON strings (especially backslashes) is challenging for small models and requires careful prompting and validation.
- **Constraint strength trade-offs:** strict constraints improve structural validity but increase implementation complexity (full JSON grammar/state machine).

## Testing strategy
- **Smoke tests using the provided dataset** (`data/input/function_calling_tests.json`) to ensure:
  - a function name is selected,
  - parameters are generated,
  - output JSON is produced and serializable.
- **Validation checks:**
  - `json.loads()` is used as a syntactic validator for parameter output.
  - Basic input validation in `FileManager.init_parse()` ensures no empty definitions/prompts and no duplicate function names.
- **Manual inspection:**
  - Printed progress output is used to inspect intermediate decoded strings during development.
